# SafeRead runtime attestation authority

SafeRead uses two deliberately separate trust configurations.

- `local`, `self_hosted`, and `development` retain the single runtime-attestation manifest and exact `OPERATOR_SAFE_READ_RUNTIME_ATTESTATION_SHA256` content pin.
- Effective hosted mode (`REVIT_OPERATOR_MODE=hosted` or `OPERATOR_HOSTED_ENABLED=true`) requires a signed runtime-attestation set and a trusted-signer ring. Each file has its own absolute path and exact SHA-256 deployment pin. Hosted mode has no single-manifest fallback, and mixing the two configuration families is rejected.

The hosted set contains 1-16 entries sorted by attestation hash and 1-16 Ed25519 signatures sorted by key ID. Each entry carries the exact runtime-attestation file bytes as `attestation_json`; its hash must equal `runtime_attestation_sha256`, so pretty-printing and trailing-newline differences cannot be hidden. The signed payload is canonical JSON over `schema`, `sequence`, `issued_at_utc`, `signer_ring`, and `entries`; `signatures` is excluded. `signer_ring` binds the exact pinned ring epoch, sequence, and file hash. An entry is selected only when both its attestation hash and complete runtime tuple exactly match the request. Every supplied signature must verify under a currently `active` key in that exact signer ring. A `revoked` signer never authorizes a set.

The capability database durably stores the highest accepted set sequence/hash and signer-ring epoch/sequence/hash. Lower sequences are rejected as rollback, different content at the same sequence is rejected as equivocation, and the authority epoch cannot silently change. Revoked signer identities and public-key hashes are durable tombstones, so later rings cannot reactivate a key or evade revocation by rebinding its material to another ID. A normal rotation increments both the signer-ring sequence and the signed-set sequence, marks predecessor keys revoked, and signs with an active successor. The set and signer ring are reloaded and re-verified immediately before the final capability compare-and-swap. High-water acceptance, revocation tombstones, and capability mint/consume changes share the same SQLite transaction.

Both configured files must be absolute, canonical paths to stable regular files. Links/reparse points, relative paths, device/FIFO inputs, files larger than their fixed admission limits, UTF-8 BOMs, malformed UTF-8, and duplicate JSON properties at any nesting depth are rejected before semantic parsing or canonicalization. Reads use a no-follow, nonblocking descriptor with pre/post identity checks and bounded allocation.

Configuration variables are documented in `.env.example`. The two checked-in `*.example.json` files contain only an ephemeral public test key, mark both signer and attestation revoked, and are intentionally incapable of authorizing a hosted request. They are schema illustrations, not deployment artifacts. Signing keys must never be placed in this repository or backend environment.
